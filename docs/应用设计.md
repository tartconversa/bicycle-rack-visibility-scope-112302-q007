# 应用设计说明

## 1. 角色与职责边界

| 角色 | 职责 | 应用支持方式 |
| --- | --- | --- |
| 评估负责人 | 决定车型配置进入受限试用或继续补样本；审批名单变更 | `evaluate` / `reconcile` / `trace` / `gaps` 提供结论、依据与溯源 |
| 车队运营人员 | 维护车辆条件、车架登记与试用范围 | `import` 持续接入资料；应用不自动改写名单，只产出建议 |

应用内所有状态变更（试用名单）都停留在「建议」层；`trial_scopes.csv` 与仓库中的
名单记录只能由人工审批后修改，系统不提供静默自动生效路径。

## 2. 时间线与历史保留

- `RackTimeline` 为每辆车索引登记区间，`resolve(vehicle_id, day)` 返回
  `active / pending / conflicted / absent` 快照及原因。
- 行程证据在评估构建时按**当时**安装状态与行程字段固化（`build_trip_evidence`）。
  后续登记更正不会修改已有行程的证据分级。
- 更正流程（`impact-rack`）需要调用方保留更正前 CSV：应用对比新旧登记，
  输出受影响车辆、行程、评估单元与待重核名单；`accepted` 名单不进入自动重核。

## 3. 证据分级与评估门槛

证据六分类见《资料契约》。评估单元键为
`model × hardware × rack_model × mount_position × region × camera_config`，
仅取 V15 行程；无车架行程不建单元，配置未确认行程并入同维度单元但：

- 不计入正向识别；
- 以「配置未确认行程」列为硬阻断，防止未核实配置支撑试用结论。

默认政策（`evaluation.Policy`，可在 CLI 显式覆盖，不能隐式放宽）：

- 可评估行程 ≥ 3；确认识别行程 ≥ 2；
- `clear` 与 `partial` 视野各至少 1 次可评估行程；
- `empty` 与 `loaded` 载荷各至少 1 次可评估行程；
- 硬红线：真实接管、确认未识别、复核已更正、配置未确认行程，任一出现即 `blocked`；
- `unobserved` / `not_evaluable` 只披露不计成功，样本量统计也不包含它们。

## 4. 名单核验与影响分析

- `reconcile`：同一 `model/hardware/rack_model/region` 下多个评估单元取最差结论；
  `accepted` 记录若证据不再达标，建议 `hold`。
- `trace`：列出范围引用的全部行程级条件（车架状态、登记号、视野、上传、
  证据分级、接管、原因），并并列行程证据版本与名单 `source_version`。
- `impact-review`：按 `review_batch` 定位被新复核触及的行程，标记非正向证据
  与待重核的 `proposed/partial` 名单。

## 5. 持久化与持续导入

- 零依赖 JSONL 仓库（`store.Store`），每表一文件 + `import_batches.jsonl`。
- 按业务主键 upsert，重复导入幂等；单表导入同样执行跨表引用校验。
- 仓库可整体删除重建，源 CSV 仍是事实来源；报告输出在 `reports/`（已 gitignore）。

## 6. 安全与运行约束

- 数据目录视为不可信输入：读取用 `utf-8-sig`，运行推荐 `python -I`，
  避免当前工作目录被植入的 `json.py` 等同名模块劫持标准库。
- 所有校验错误抛 `MaterialError` 并带文件名、行号与字段名，不做静默纠正。
- 合成数据生成器 `tools/generate_data.py` 输出到独立空目录，拒绝覆盖契约文件。

## 7. 测试布局

| 文件 | 覆盖内容 |
| --- | --- |
| `tests/test_materials.py` | 基线 CSV 表头、行数、遗留文件清理 |
| `tests/test_loader.py` | 枚举/日期/主键/引用完整性校验 |
| `tests/test_timeline.py` | 区间判定、冲突、六种证据分级、占位接管 |
| `tests/test_pipeline.py` | 幂等导入、三类评估结论、名单核验、溯源、两类影响分析、CLI |
